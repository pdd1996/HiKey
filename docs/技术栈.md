## 2. 各层详解

### 2.1 桌面框架：Electron

**职责：** 提供"用 Web 技术做桌面应用"的能力。把 Chromium（渲染界面）+ Node.js（系统能力）打包成一个应用。

**选型理由：**
- JS/TS 全栈生态最成熟，出活快
- 主进程可直接用 Node API（文件、网络、safeStorage）
- 渲染进程用 React 开发，和 Web 开发体验一致

**代价：** 安装包体积大（~150MB），内存占用高。个人开发者本地工具可接受。

**版本：** 固定 Electron 主版本（开发时锁定具体版本号，写入 `package.json`，避免构建链中途漂移；升级时主动评估）。

### 2.2 构建工具：electron-vite

**职责：** Electron 应用有三个构建目标，electron-vite 用一套 Vite 配置统一处理：
- `main`：主进程（Node 环境）
- `preload`：预加载脚本（Node + 浏览器混合环境）
- `renderer`：渲染进程（浏览器环境，React）

**选型理由：**
- 当前 Electron + Vite 的主流方案
- 开箱支持 TypeScript、热更新（HMR）
- 比 electron-forge 配置更简洁，比手写 webpack 现代

**替代方案对比：**

| 方案 | 评价 |
|---|---|
| electron-vite | ✅ 选这个，最省心 |
| electron-forge | 官方推荐但配置繁琐 |
| 手写 webpack | 过时且复杂 |

### 2.3 打包：electron-builder

**职责：** 把开发好的应用打包成 Windows 安装包（`.exe` / NSIS 安装程序）。

**选型理由：**
- Electron 生态最成熟的打包工具
- 配置简单（一个 `electron-builder.yml`）
- 支持自动更新、代码签名（MVP 不做）

### 2.4 前端框架：React 18 + TypeScript

**职责：** 渲染进程的 UI--Dashboard、列表、表单、对话框、设置页。

**选型理由：**
- 生态最大、组件库最多
- TypeScript 是必选：主进程也用 TS，统一语言减少切换成本

### 2.5 UI 组件库：shadcn/ui + Tailwind + Radix

三个东西配合，不是三个独立选择：

| 组件 | 角色 |
|---|---|
| **Radix UI** | 无样式的行为引擎，负责弹窗/菜单/开关的交互逻辑和无障碍（键盘导航、焦点管理、aria 属性） |
| **Tailwind CSS** | 原子化 CSS，给 shadcn 组件提供样式 |
| **shadcn/ui** | 在 Radix 外面包 Tailwind 样式，组件源码直接复制进项目 |

**选型理由：**
- shadcn 不是传统依赖库，是"复制源码进项目"，体积几乎为零，完全可控
- 视觉天然偏桌面、紧凑现代
- Radix 保证无障碍和键盘交互
- 唯一代价是要配 Tailwind，但 Tailwind 在 Electron 里很顺

**HiKey 会用到的 shadcn 组件：**

| 组件 | 用途 |
|---|---|
| Dialog | 添加/编辑 key 的弹窗 |
| AlertDialog | 删除/查看明文的二次确认 |
| DropdownMenu | 列表行的操作菜单（查看/编辑/删除） |
| Switch | 轮询深检开关、明文降级开关 |
| Tooltip | 错误详情悬浮提示 |
| Tabs | Dashboard / 设置页切换 |
| Table | key 列表 |
| Button / Input / Select / Badge | 表单元素、状态徽标 |

### 2.6 数据库：lowdb

**职责：** 主进程读写 `hikey-db.json`，存 key 记录和全局设置。

**选型理由：**
- 零 native 依赖，打包不踩 `electron-rebuild` 的坑
- 几十到几百条记录，JSON 完全够用
- 备份恢复为带 verifier 校验标识的 `.hikey-backup` 打包文件（非简单复制 hikey-db.json）
- v2 要做用量历史时再迁 SQLite

**替代方案对比：**

| 方案 | 评价 |
|---|---|
| lowdb | ✅ 平衡了简单和结构化 |
| better-sqlite3 | 真 SQL 但要 native 编译，打包坑多，MVP 不值 |
| electron-store | 太简单，偏配置存储，不支持数组查询 |

### 2.7 加密：Electron safeStorage

**职责：** 加密 key 的 secret 字段。Windows 上走 DPAPI，密钥由操作系统管理。

**选型理由：**
- 底层使用 Windows DPAPI，保护范围为同一 Windows 用户；**不等同于 Chrome/Edge 的 App-Bound Encryption**，不承诺同级防护
- 用户无感，不用记主密码
- 代码极简：`safeStorage.encryptString()` 一行
- 密钥不在代码里，由 OS 内核管理

**不选主密码 + argon2 + AES 的原因：**
- 每次启动输密码，体验负担重
- 自己写加密代码 = 自己背安全责任
- OS 账号已沦陷时，HiKey 单独保住 key 意义不大（木桶短板不在 HiKey）

### 2.8 导入解析：dotenv + JSON.parse

**职责：** 解析 `.env` 文件和 JSON 文件，批量导入 key。

**选型理由：**
- dotenv 是成熟库，解析 `.env` 无坑（处理引号、注释、空行）
- JSON 用原生 `JSON.parse`，零依赖
- 限制：主进程文件选择框选文件，限制 `.env`/`.json` 且 ≤ 1MB

## 4. 进程职责划分

技术栈落地到 Electron 的三个进程：

```
主进程（main / Node 环境）
├ Electron API
│   ├ 窗口创建与生命周期
│   ├ safeStorage（加解密）
│   ├ dialog（文件选择/保存）
│   ├ app.getPath（userData 路径）
│   └ ipcMain（注册 IPC handler）
├ lowdb（数据库读写，原子写 temp+rename+fsync）
├ healthCheck（fetch 调 LLM API，ping + 深检）
├ scheduler（定时轮询，并发控制）
├ importer（dotenv + JSON.parse，去重预览）
└ backup（备份恢复，verifier 校验，原子写）

preload（Node + 浏览器混合环境）
└ contextBridge（暴露最小安全 API 给渲染进程）
    └ 明文 key 不外泄：keys:list 不含 encSecret

渲染进程（renderer / 浏览器环境）
├ React + TypeScript
├ shadcn/ui + Tailwind + Radix
├ 调用 window.hikey.* IPC 接口
└ 不直接接触文件系统、数据库、明文 key
```

### 4.1 进程间通信（IPC）

渲染进程不直接访问主进程能力，通过 IPC 通道调用：

```typescript
// 主进程注册
ipcMain.handle('keys:list', () => {
  return db.data.keys.map(({ encSecret, ...rest }) => rest)  // 剥离密文
})

// preload 暴露
contextBridge.exposeInMainWorld('hikey', {
  keys: {
    list: () => ipcRenderer.invoke('keys:list'),
    reveal: (id: string) => ipcRenderer.invoke('keys:reveal', id),
  }
})

// 渲染进程调用
const keys = await window.hikey.keys.list()
```

### 4.2 安全边界

| 配置 | 值 | 作用 |
|---|---|---|
| `contextIsolation` | `true` | 隔离 preload 和渲染进程上下文 |
| `nodeIntegration` | `false` | 渲染进程不能用 Node API |
| `sandbox` | `true` | 沙箱化渲染进程 |
| CSP | 启用 | 禁止外部导航与远程内容加载 |

## 5. 不用的技术（明确排除）

| 技术 | 为什么不用 |
|---|---|
| Tauri | 选了 Electron（JS/TS 全栈，出活快） |
| Vue | 选了 React |
| SQLite / better-sqlite3 | native 编译坑多，lowdb 够用 |
| 主密码 + argon2 + AES | 改用 safeStorage，无需主密码 |
| MUI | Material 风格不适合桌面应用 |
| Ant Design | 后台管理系统味道太重 |
| Express / Fastify | 不需要后端服务器 |
| 任何云服务 | 零云端定位，数据完全本地 |

## 6. 出站请求

HiKey 运行时，主进程会直接请求用户配置的 LLM 厂商 API（不经过任何中间服务器）：

| provider | ping 端点 | 深检端点 |
|---|---|---|
| openai | `GET https://api.openai.com/v1/models` | `POST .../v1/chat/completions` |
| anthropic | `GET https://api.anthropic.com/v1/models` | `POST .../v1/messages` |
| deepseek | `GET https://api.deepseek.com/v1/models` | `POST .../v1/chat/completions` |
| custom | `GET {用户baseUrl}/models`（原样拼接，不追加 /v1） | `POST {用户BaseUrl}/chat/completions`（原样拼接） |

所有请求从用户电脑直接发给厂商，HiKey 不做中间代理。
