## 1. 存储方案

### 1.1 选型：lowdb（JSON 文件存储）

| 维度 | 决策 |
|---|---|
| 存储引擎 | lowdb（基于 JSON 文件的轻量数据库） |
| 文件格式 | 单个 JSON 文件 |
| 运行位置 | 主进程 |
| 依赖 | 零 native 依赖，纯 JS |

**为什么不用 SQLite：**
- 数据量小：几十到几百条 key 记录，JSON 完全 hold 住
- 零 native 依赖：打包不踩 `electron-rebuild` 的坑
- 备份恢复：打包为带 verifier 校验标识的 `.hikey-backup` 文件（非简单复制 hikey-db.json）
- v2 若做用量历史（每次调用记一条 token 消耗），再迁 SQLite，数据迁移脚本几十行

### 1.2 文件位置与写入

| 项 | 说明 |
|---|---|
| 文件路径 | `app.getPath('userData')/hikey-db.json`（Windows: `%APPDATA%/HiKey/`） |
| 写入策略 | **temp + rename + fsync 原子写**，避免写到一半崩溃损坏数据 |
| lowdb 配置 | 自定义 adapter 包装 `JSONFile`，写入时走 temp + rename + fsync（lowdb v7 的 `JSONFile` 不自带原子写，需自行实现） |

### 1.3 访问边界

- **仅主进程**读写数据库文件
- 渲染进程通过 IPC 获取数据，**永不直接接触文件**
- `keys:list()` 返回的列表**不含明文 secret**（encSecret 字段不外泄到渲染进程）
- 明文仅在 `keys:reveal(id)` 时经 IPC 一次性返回

## 2. 整体结构

单文件 JSON，三个顶层部分：

```
hikey-db.json
├── schemaVersion: 2        ← 版本号，用于迁移
├── keys: [ ... ]            ← key 记录数组（主体）
└── meta: { ... }            ← 全局设置
```

完整示例：

```json
{
  "schemaVersion": 2,
  "keys": [
    {
      "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "name": "我的OpenAI",
      "provider": "openai",
      "baseUrl": "https://api.openai.com",
      "encSecret": "<safeStorage密文base64>",
      "secretMode": "safeStorage",
      "status": "valid",
      "lastChecked": 1691000000000,
      "lastCheckMode": "deep",
      "lastDeepCheckedAt": 1691000000000,
      "lastError": "",
      "deepCheck": true,
      "testModel": "gpt-4o-mini",
      "createdAt": 1690900000000,
      "updatedAt": 1691000000000,
      "notes": "工作账号"
    }
  ],
  "meta": {
    "checkIntervalMinutes": 15,
    "deepCheckEnabled": false,
    "concurrentChecks": 4,
    "pingTimeoutMs": 2000,
    "deepTimeoutMs": 2000,
    "allowPlaintextFallback": false,
    "plaintextMode": false,
    "clipboardClearMs": 60000
  }
}
```

## 3. keys 数组：单条记录字段

字段按用途分四组。

### 3.1 身份信息

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string (uuid) | 是 | 主键，唯一标识。用 uuid 不用自增整数，避免导入/恢复时冲突 |
| `name` | string | 是 | 用户起的名字，如"我的OpenAI"。**不唯一**（同 key 可多 name） |
| `provider` | enum | 是 | `openai` / `anthropic` / `deepseek` / `custom`。决定用哪套检测逻辑 |
| `baseUrl` | string | 是 | API 根地址，如 `https://api.openai.com`。非 custom：代码自动剥离版本后缀（`/v1`）再拼回 `/v1`；custom：原样拼接不追加版本段，用户自负责填对路径 |
| `notes` | string | 否 | 备注，纯文本。**明确规定不用于存放密钥** |

### 3.2 敏感信息（加密存储核心）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `encSecret` | string | 是 | secret 的存储值（base64）。正常模式为 safeStorage 加密后的密文；明文降级模式下为明文。**明文只存在于该字段，由 secretMode 标识当前是密文还是明文** |
| `secretMode` | enum | 是 | `safeStorage` / `plaintext`。自描述该条 secret 是密文还是明文 |

**为什么 encSecret 和 secretMode 要分开：**

读取时程序先看 `secretMode` 决定"要不要解密"：
- `safeStorage` -> 调 `safeStorage.decryptString(encSecret)` 解密
- `plaintext` -> 直接用 encSecret 的值（降级模式下的明文记录）

如果不分字段，程序无法区分"这串是密文"还是"这串是明文"，会对明文调解密直接报错。

**新增记录时的写入规则：**
- safeStorage 可用 -> 强制 `safeStorage`（即使用户误开降级也不主动明文存）
- safeStorage 不可用 + 用户已显式开启明文降级 -> 写 `plaintext`
- safeStorage 不可用 + 未开启降级 -> fail-closed，拒绝写入

### 3.3 检测结果

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `status` | enum | 是 | 当前状态（见下方枚举） |
| `lastChecked` | number (ms) | 否 | 上次检测（ping 或深检）的时间戳 |
| `lastCheckMode` | enum | 否 | `ping` / `deep` / `null`。上次检测做了哪级，重启后能还原 UI 显示 |
| `lastDeepCheckedAt` | number (ms) | 否 | 上次深检的时间戳。和 lastChecked 分开，因为深检不是每次都做 |
| `lastError` | string | 否 | 脱敏后的错误信息。**不含 URL query、Authorization、明文 key** |

**status 枚举：**

| 值 | 含义 | 徽标颜色 |
|---|---|---|
| `checking` | 检测进行中 | 蓝 |
| `valid` | 检测通过，key 可用 | 绿 |
| `invalid` | 401/403 且非欠费，key 失效 | 红 |
| `rate_limited` | 429 且非欠费，被限流 | 黄 |
| `quota_exceeded` | 欠费/余额不足 | 橙 |
| `unknown` | 5xx/超时/网络异常，不确定 | 灰 |
| `unchecked` | 从未检测过 | 灰 |

**为什么 lastChecked 和 lastDeepCheckedAt 分开：**

深检只在"新增/编辑/手动"时触发，轮询只 ping。用户可能想看"这个 key 上次深检是什么时候"和"上次 ping 是什么时候"两个不同的时间点。

**lastError 脱敏规则：**
- 只存：HTTP 状态码 + 错误码字符串（如 `403 / billing_not_active`）
- 过滤掉：请求 URL（可能含 key）、Authorization 头、响应体中的原始 key
- 模型/配置错误写：`深检未通过：模型/配置问题，建议更换 testModel`

### 3.4 配置和元数据

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `deepCheck` | boolean | 是 | `true` | 该记录是否启用深检。和全局 `deepCheckEnabled` 是 AND 关系（仅影响轮询；手动/新增/编辑始终可深检） |
| `testModel` | string | custom 必填 | 按 provider 预填 | 深检用的模型名，如 `gpt-4o-mini`。所有 provider 可配 |
| `createdAt` | number (ms) | 是 | - | 创建时间戳 |
| `updatedAt` | number (ms) | 是 | - | 最后修改时间戳 |

**deepCheck 两级开关逻辑（仅影响轮询）：**

```
轮询深检执行 = 全局 deepCheckEnabled(开) AND 记录 deepCheck(true) AND ping=valid
```

手动/新增/编辑触发的深检不受这两个开关限制（始终可深检）。为什么是单条记录级而不是全局：用户可能想"OpenAI 的 key 都深检，但 custom 的 key 不深检（怕花钱）"。单条 + 全局 AND 是最灵活的组合。

**testModel 默认值（MVP 首版暂定，M3 复核定稿）：**

| provider | 默认 testModel |
|---|---|
| openai | `gpt-4o-mini` |
| anthropic | `claude-3-5-haiku-latest` |
| deepseek | `deepseek-chat` |
| custom | 无默认，用户必填 |

## 4. meta 对象：全局设置

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `checkIntervalMinutes` | number | `15` | 轮询间隔，范围 5~1440 分钟 |
| `deepCheckEnabled` | boolean | `false` | 轮询时是否深检。和单条 `deepCheck` 是 AND；关闭则轮询仅 ping（新增/编辑/手动深检不受此限） |
| `concurrentChecks` | number | `4` | 并发检测上限 |
| `pingTimeoutMs` | number | `2000` | ping 超时（毫秒） |
| `deepTimeoutMs` | number | `2000` | 深检超时（毫秒） |
| `allowPlaintextFallback` | boolean | `false` | 明文降级开关。仅 safeStorage 不可用时可开；不可用时开了不可关（置灰） |
| `plaintextMode` | boolean | `false` | 当前是否处于明文模式。重加密全部完成后置回 false |
| `clipboardClearMs` | number | `60000` | 剪贴板清除延迟（毫秒）。清除前由主进程比对内容一致才清 |

**allowPlaintextFallback 与 plaintextMode 的关系：**
- `allowPlaintextFallback` = 用户是否"允许"明文降级（开关）
- `plaintextMode` = 当前是否"实际处于"明文模式
- safeStorage 不可用 + 用户开开关 -> `allowPlaintextFallback=true`，新增记录写 `plaintext`，`plaintextMode` 置 `true`
- safeStorage 恢复 + 重加密全部完成 -> `plaintextMode` 置 `false`，`allowPlaintextFallback` 可由用户关闭

## 5. schemaVersion 与迁移

### 5.1 当前版本

`schemaVersion: 2`（v1.8 升级，用于触发 gemini 等未知 provider 的迁移）

### 5.2 迁移策略

- 启动时读取 `schemaVersion`，**字段缺失视为 0**；低于当前版本（2）则自动迁移并写回
- 迁移失败则中止启动、提示用户从备份恢复，**不破坏原库**
- 迁移采用 temp + rename 原子写

### 5.3 未知 provider 处理

场景：v1.6 前历史库里的 `gemini` 记录，当前版本已移除 Gemini 支持。

处理规则：
- 迁移时将该记录 `provider` 改为 `custom`
- `lastError` 写：`原 provider=gemini，已迁移为 custom，请确认 baseUrl/testModel`
- UI 提示用户手动处理（确认 baseUrl/testModel 或删除）

## 6. 状态流转

### 6.1 检测流程

```
启动检测
  │
  ├─ 归位：遗留 checking -> unchecked
  │
  └─ 对每条 key：
       │
       ├─ status = checking（写入，UI 显示蓝牌）
       │
       ├─ ping（GET /models）
       │    ├─ 200 -> valid
       │    ├─ 401/403 + 欠费码 -> quota_exceeded
       │    ├─ 401/403 其他 -> invalid
       │    ├─ 402 或 429 + 欠费码 -> quota_exceeded
       │    ├─ 429 无欠费码 -> rate_limited
       │    ├─ 5xx/超时 -> unknown
       │    └─ 其余 4xx -> unknown（不误判失效）
       │
       ├─ ping != valid -> 结束，不深检
       │
       └─ ping == valid + 深检前置条件满足？
            ├─ 不满足 -> status 保持 valid，lastCheckMode=ping
            └─ 满足 -> 深检
                 ├─ 2xx -> valid，lastCheckMode=deep
                 ├─ 401/403/402/429 -> 按 ping 同规则改状态
                 ├─ 400/404 -> 状态保持 valid（不降级），lastError 写模型/配置问题
                 ├─ 5xx/超时 -> unknown
                 └─ 其余 4xx -> unknown（不猜测原因）
```

### 6.2 深检前置条件

```
深检执行 = ping == valid
         AND (
           触发时机 = 新增/编辑/手动（始终深检，bypass 开关）
           OR (轮询 AND 全局 deepCheckEnabled(开) AND 记录 deepCheck(true))
         )
```

### 6.3 启动归位

应用启动时：
- 所有 `status === "checking"` 的记录 -> 归位为 `unchecked`
- 理由：上次检测未完成（关窗/崩溃），结果未知，不能停留在"检测中"

## 7. 加密与明文降级

### 7.1 正常模式（safeStorage 可用）

```
写入：plaintext -> safeStorage.encryptString() -> encSecret (base64)
      secretMode = "safeStorage"

读取：encSecret -> safeStorage.decryptString() -> plaintext
```

### 7.2 明文降级模式（safeStorage 不可用 + 用户显式开启）

```
写入：plaintext -> 直接存（不加密）
      secretMode = "plaintext"
      plaintextMode = true

读取：encSecret 字段即明文，不调解密
```

### 7.3 重加密（safeStorage 恢复后）

```
触发：safeStorage 从不可用变为可用

流程：
  对每条 secretMode === "plaintext" 的记录：
    plaintext -> safeStorage.encryptString() -> 新 encSecret
    secretMode = "safeStorage"

完成：
  全部成功 -> plaintextMode = false，UI 警告消失，allowPlaintextFallback 可关
  部分失败 -> 保留明文，lastError 记录原因，UI 警告"N 条记录仍为明文"
```

### 7.4 明文降级开关状态机

| safeStorage 状态 | 开关状态 | 可否操作 | 说明 |
|---|---|---|---|
| 可用 | 不显示 | - | 开关仅在 safeStorage 不可用时显示 |
| 不可用 | 关 | 可开 | 默认 fail-closed，拒绝写新 secret |
| 不可用 | 开 | **不可关（置灰）** | 无法重加密，需 safeStorage 恢复后自动重加密完成才可关 |

## 8. 备份与恢复

### 8.1 备份文件格式

`.hikey-backup` 为 JSON 打包：

**密文备份（safeStorage 可用时）：**
```json
{
  "schemaVersion": 2,
  "keys": [ ... ],
  "meta": { ... },
  "verifier": "<safeStorage 加密的校验标识>",
  "plaintextBackup": false,
  "plaintextRecordCount": 0
}
```

**明文标记备份（safeStorage 不可用时）：**
```json
{
  "schemaVersion": 2,
  "keys": [ ... ],
  "meta": { ... },
  "verifier": null,
  "plaintextBackup": true,
  "plaintextRecordCount": 3
}
```

- `verifier`：一段固定文本经 safeStorage 加密后的密文，用于恢复时校验"是否本机备份"
- `plaintextBackup`：布尔标记。`false`（密文备份）走 verifier 校验；`true`（明文标记备份）跳过 verifier，强制二次确认 + 醒目警告"明文导出，任意机器可读"
- `plaintextRecordCount`：库内 secretMode=plaintext 的记录数。**无论密文备份还是明文标记备份都写入**；>0 时 UI 提示"备份包含 N 条明文记录，请妥善保管"（密文备份也可能因重加密部分失败而含明文记录）
- 字段组合校验：verifier 与 plaintextBackup 组合必须合法（verifier 非 null 则 plaintextBackup=false；plaintextBackup=true 则 verifier=null），非法组合拒绝恢复
- 内部结构 M3 定稿

### 8.2 恢复识别

| 场景 | 处理 |
|---|---|
| 明文标记备份（plaintextBackup=true，verifier=null） | 跳过 verifier 校验；强制二次确认 + 醒目警告"明文导出，任意机器可读"；混合库（plaintext + safeStorage 记录并存）不拒绝恢复，safeStorage 记录按旧密文读取规则标 unknown 并提示；恢复后立即执行 schema 迁移 + 重加密 |
| 密文备份-同机（verifier 解密成功） | 允许恢复；含 plaintext 记录时恢复后自动触发重加密 |
| 密文备份-跨机（verifier 解密失败） | 整体拒绝，不做部分恢复，不破坏当前库 |
| 畸形字段组合 | verifier=null 但 plaintextBackup 缺失/false，或 plaintextBackup=true 但 verifier 非 null -> 拒绝恢复并报错 |

### 8.3 恢复流程

```
1. 用户选备份文件
2. 字段组合校验（verifier 与 plaintextBackup 合法性）
   └─ 非法组合 -> 拒绝恢复，报错
3. 检查备份标记
   ├─ plaintextBackup=true（明文标记备份）
   │   └─ 强制二次确认 + 醒目警告"明文导出" -> 继续
   └─ 密文备份 -> 解密 verifier 校验
       ├─ 失败 -> 拒绝，报错"非本机备份"
       └─ 成功 -> 继续
4. 预备份当前库
   ├─ 当前库可读 -> 导出到 userData/backups/hikey-db.pre-restore.{timestamp}.hikey-backup
   │   ├─ 成功 -> 继续
   │   └─ 失败 -> 中止恢复
   └─ 当前库损坏 -> 跳过预备份，继续恢复
5. 原子写入：temp + rename + fsync
   ├─ 成功 -> 继续
   └─ 失败 -> 旧库完好（temp 文件丢弃），报错
6. 恢复后立即执行 schema 迁移（处理旧备份 schemaVersion<2 且含 gemini 等未知 provider）
   ├─ 成功 -> 继续
   └─ 失败 -> 回滚到恢复前状态，报错
7. 含 plaintext 记录 -> 触发重加密（plaintext 记录可读，safeStorage 密文记录保留标 unknown）
7. 恢复完成
```

### 8.4 预备份保留策略

- 位置：`userData/backups/`
- 保留最近 3 个 `hikey-db.pre-restore.{timestamp}.hikey-backup`
- 超出的自动删除

## 9. 索引与查询

lowdb 无原生索引，基于数组 filter/select。当前数据量（几十~几百条）性能完全够。

常用查询模式（基于 lowdb v7，操作 `db.data` 下的数组，需手动 sort/filter）：

| 查询 | 实现 |
|---|---|
| 列表全部（不含明文） | `db.data.keys.map(({ encSecret, ...rest }) => rest)` |
| 按 id 查 | `db.data.keys.find(k => k.id === id)` |
| 按 provider 筛选 | `db.data.keys.filter(k => k.provider === provider)` |
| 按状态筛选 | `db.data.keys.filter(k => k.status === status)` |
| 按 provider 排序 | `[...db.data.keys].sort((a, b) => a.provider.localeCompare(b.provider))` |
| 读取明文（仅 reveal） | `find(k => k.id === id) -> 按 secretMode 解密或直取 -> 返回一次性明文` |

v2 若数据量上来（用量历史记录），迁 SQLite 后再加索引。

## 10. 字段速查表

| 字段 | 类型 | 分组 | 加密 | 渲染进程可见 |
